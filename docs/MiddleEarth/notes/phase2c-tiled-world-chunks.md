# Phase 2c: the world as a chunked Tiled world

The single 900×900 `middleearth.tmx` was too laggy in Tiled, and moving the reference image into place was close to impossible. User: *"I would actually prefer to edit the whole tiled world in the end, even with the clutter and everything. For that I would probably need a tiledworld anyway to not need the full map loaded."*

The world is now a Tiled world of 36 chunk maps plus a generated overview map for checking against the reference image. The game builds exactly the same world from it as before.

## Format

Everything is in `MiddleEarth/world/middleearth/`. `world.json` → `"worldMap": "world/middleearth/middleearth.world"`.

| File | Content |
| --- | --- |
| `middleearth.world` | Tiled world (JSON, `"type": "world"`). One entry per chunk: `fileName`, `x`, `y`, `width`, `height` in **pixels**. Written in Tiled's own layout (keys sorted, 4-space indent), so a save from Tiled doesn't change it. `"onlyShowAdjacentMaps": true` (see below). |
| `chunk_<col>_<row>.tmx` | 6×6 chunks of **150×150 tiles** (2400×2400 px). `chunk_0_0` is the north-west corner, `col` goes east, `row` goes south. Same layers as the Phase 2b map: tile layer `Biomes`, object layer `POI` with **chunk-local** coordinates (0–2400 px). The `start` object is in the chunk that holds it (`chunk_1_3`). |
| `chunk_0_0.tmx` map properties | `seed`: the world-level properties live on chunk_0_0. This is a plain map property that Tiled edits normally (Map → Map Properties). The `.world` format has no properties of its own that Tiled reliably keeps on save, and a separate meta file couldn't be edited in Tiled. The reader takes `seed` from any chunk; if more than one chunk sets it, the reader logs it and `check.sh` reports an error. |
| `biomes.tsx` + `biomes.png` | The biome tileset, unchanged (moved here from `world/`). |
| `overview.tmx` + `overview.png` | Generated overview, see below. |
| `map-of-middle-earth.jpg` | The user's reference image (commit `bc65e3002`), moved here from `world/`. |

**Chunk size.** 150 divides 900, so all chunks have the same size. Each chunk has 22,500 tiles, 1/36 of the old map. With `onlyShowAdjacentMaps` Tiled shows at most 3×3 chunks = 202,500 tiles (450×450), a quarter of the old 810,000, and only one chunk (22,500 tiles) is the editable document. 100×100 chunks (81 maps) would make the neighbourhood smaller (90,000 tiles) but would mean many more files and border crossings for POIs and painting. 225×225 (16 maps) would give 455,000 tiles in the neighbourhood, more than half of the old map. 150 is the middle ground. To change it later, run `exportWorldTmx <dir> <size>`; the edge chunks may then be smaller.

**Lossless migration.** The game loaded the user's Tiled-saved `middleearth.tmx` (Tiled 1.12.2, including **38 hand-painted tiles** around tile 749,275 that the Phase 2b file didn't have). Then `exportWorldTmx world/middleearth` wrote the chunks. The decoded chunks are identical to that tmx: 810,000/810,000 cells, 98/98 objects (97 POIs + start) with the same names, positions and properties, and the same seed. The reader ignores the tmx's extra `reference` tileset (gid 49) and the `Reference` object group, because it only reads tiles with a `biome` property, the `Biomes` layer and the `POI` group. The old `world/middleearth.tmx` and `world/biomes.tsx/png` are deleted.

### `onlyShowAdjacentMaps`

From Tiled's documentation (Working with Worlds) and its source (`World::contextMaps`): when a map that belongs to a loaded world is open, Tiled also loads the world's other maps as read-only "context" maps and draws them around the current one.

- `false` (Tiled's default): **all** maps of the world are loaded (each one fully parsed as a map document) and shown. There is no lazy loading by viewport. Qt's scene only skips painting what is off screen. Zoomed out, that is all 810,000 tiles again, so it is no faster than the single map.
- `true`: only the maps whose rectangle touches the current map's rectangle (grown by 1 px) are loaded and shown, which is the current chunk plus its up to 8 neighbours. When another chunk becomes the current map, the neighbourhood moves with it and the newly adjacent maps are loaded.

Only the current map is ever editable. You make a neighbour current by clicking into it (or opening it). So we use `true`: the whole world can still be edited chunk by chunk, and `overview.tmx` gives the full picture. To see everything at once, set it to `false` (expect the old lag when zoomed out).

### Overview map

`overview.tmx` is **generated by `exportWorldTmx`** and not read back (decision: generated, not edited back). It is not part of the `.world`, because it would overlap the chunks.

- Map: 6×6 tiles of 150×150 px, so **one grid cell is one chunk** and 1 px is 1 world tile (900×900 px in total).
- `Biomes`: an **image layer** with `overview.png` (each tile's biome colour, 1 px per tile; locked). One image draw instead of 810,000 tile draws, so panning and dragging stay smooth. A 1-px tileset would still draw 810,000 tiles.
- `Reference`: image layer with `map-of-middle-earth.jpg` at its natural 1600×900 size, opacity 0.6. The user's scale (the 1600×900 image stretched to 25,600×14,400 world px, so 1 image px = 16 world px = 1 tile) is exactly the overview's 1 px = 1 tile, so no scaling is needed. Their placement in the old tmx (object group offset −8656.9/8867.95 plus the tile object at 5164.91/6151.75, bottom-left anchored) converts to `offsetx="-218.25" offsety="38.73"` (top-left, in world tiles). The image is 1600 tiles wide, much wider than the 900-tile world. The user said it was not placed carefully, so it should now be aligned in the overview by dragging the layer (Select Layer tool / Offset). **A re-export keeps this layer** (offset, opacity, visibility, image) and regenerates everything else. Without an old overview, an empty `Reference` slot is written.
- `Chunks`: one rectangle per chunk, named after the chunk file (locked).
- `POI`: point labels (display name; type = POI entry) and the start (locked).

## Engine changes (for PLAN.md → "Engine changes")

| Change | Files |
| --- | --- |
| `WorldMapTmx.read` also takes a `.world` file. It parses every chunk with the Phase 2b tmx parser (moved into `parseMap`), offsets chunk-local objects to world coordinates and assembles one biome array, so the result is the same data as for a single map. New fields: `chunks` (file, x/y/size in tiles, POI count) and `problems` (chunk off the tile grid, different tile sizes, overlapping chunks, tiles in no chunk, an object outside its chunk, several seeds, several starts; also logged). A single `.tmx` still works. World `patterns` are not supported. | `forge-gui-mobile/.../world/WorldMapTmx.java` |
| `WorldMapTmx.writeWorld(dir, name, …, chunkSize)`: chunks, `.world`, tileset, overview (keeps the old overview's `Reference` layer). The tmx writer is shared by both formats (`mapXml`). | same |
| `World.exportWorldTmx(file, chunkSize)`: a `.tmx` path writes one map as before. A directory or `.world` path writes the chunked world, with chunk size 0 = the current world's chunk size, else 150. The console command is `exportWorldTmx [dir \| file.world \| file.tmx] [chunkSize]` (default `~/.forge/adventure/world/`). | `.../world/World.java`, `.../stage/ConsoleCommandInterpreter.java` |

`World.generateNew` is unchanged: `loadWorldMap()` calls `WorldMapTmx.read`, which now accepts either format.

## Tools

- **PlaneCheck** (`check.sh`): for a `.world`, the Phase 2b checks for each chunk (tileset, gids → biomes, POI entries), plus the chunk checks from the engine reader as errors (exact tiling, no gaps, no overlaps, objects inside their chunk, the size matches `world.json`), a warning if a `.world` entry's pixel size doesn't match its chunk, `seed` on exactly one chunk, exactly one start, and the overview and its reference image exist (warnings). Output: `worldMap world/middleearth/middleearth.world: 36 chunks of 150 tiles, 900x900, seed …, 44/44 biomes painted, 97 POI objects (89 distinct), 1 start`.
- **WorldSim**: reads the `.world` through `WorldMapTmx.read` and counts the reader's `problems` (`CHUNKS: …`) plus the Phase 2b checks.
- **game.sh smoke** now exports `.me-test/smoke-world/` (the chunked world; a two-run determinism check is `diff -r`).
- `tools/middleearth/biomemap/make_biome_map.py`: the header points to the `.world`.

## Phase 2d design: editing everything (terrain, structures, clutter, roads)

What `World.generateNew` still generates from `seed`, apart from biome and POIs:

1. **Terrain variant per tile** (`terrainMap`, low bits): noise picks a biome's `terrain[]` entry (e.g. `Green_1`, `Green_2` from `world/tilesets/terrain.atlas`), 0 = the base tile. Plus a collision bit.
2. **Structures** (`terrainMap` + `isStructureBit`): WFC output per biome `structures[]` (mountains, forests, the Mordor ring), anchored on the biome's bounding box. The index is `terrain.length + 1 + structure offset + mappingInfo index`, with a collision bit per structure tile.
3. **Biome borders**: computed at render time from neighbouring tiles (not stored). Nothing to edit.
4. **Roads**: the road bit in `biomeMap`, drawn as lines between each town and its nearest town; the hidden POI→town paths clear the collision in `terrainMap`.
5. **Clutter** (`mapObjectIds`, a `SpritesDataMap`): sprites from `biomesSprites` (trees, rocks, shells) at random sub-tile positions, chosen by noise and density per biome `spriteNames`.
6. `clearTerrain` around POIs and the start.

Proposed per-chunk layers (all optional; **a layer that is present replaces its generation step, a missing layer is generated as today**):

| Layer | Type | Content | Import | Export |
| --- | --- | --- | --- | --- |
| `Terrain` | tile layer | One tileset per terrain atlas (`terrain.atlas` and the other `world/tilesets/*.atlas`, cut into 16-px tiles as `.tsx` with an image of the atlas page) plus one tileset per structure atlas. Tile properties: `terrain=<spriteName>` or `structure=<sourcePath>#<mappingInfo name>`, `collision=true` where the structure has collision. It renders like the game, minus the autotile borders. | After the biome pass: if any chunk has `Terrain`, set `terrainMap[x][y]` from the tile property (translated to the biome-relative index), skip the noise and WFC for those tiles, and set `isStructureBit`/`collisionBit`. Biome masks and borders as today. | From `terrainMap`: index → sprite/structure name → gid. |
| `Roads` | tile layer | One "road" tile (from `road.atlas`, property `road=true`). | If present: set the road bit from the layer and skip road building. The hidden POI paths stay generated (or a second `Paths` layer could hold them). | From the road bit in `biomeMap`. |
| `Clutter` | object layer | Tile objects with the sprite's image from `map_sprites.json` (tileset as an image collection, property `sprite=<key>`), at the exact position. | If present in a chunk: skip the clutter loop for that chunk and `putPosition` each object. | From `mapObjectIds.positions(...)`, converted to chunk-local Tiled coordinates (tile objects are bottom-left anchored). |

Per-layer, per-chunk skipping keeps the generator as the fallback. The user can start with exported layers (everything filled from the seed) and edit them, or delete a layer to get generation back. `exportWorldTmx` writes every layer that exists, so the round trip stays byte-identical.

Effort estimate:

- `Roads`: about 0.5 day (one tile, one bit, skipping road building in `generateNew`).
- `Clutter`: about 1 day (image-collection tileset from the sprite atlas, positions, a skip per chunk; the `SpritesDataMap` chunking is by the game's own 150-tile chunk size, not ours).
- `Terrain` + structures: about 2–3 days. The atlas → tsx conversion is the main work (atlas regions, autotile pages; a generated tsx per atlas with per-tile properties). The index mapping is fiddly (structure offsets per biome), and the minimap must keep working.
- Checks, docs, tests: about 1 day.
- Total: **about 4–5 days**. Chunk files grow by about 2 layers; clutter is about 40–80k objects, roughly 1,000–2,000 per chunk.

**Not implemented now.** An exported-but-ignored `Roads` or `Clutter` layer would invite edits that silently disappear on the next new game. Export and import should land together in 2d.

## Open questions

- **Tiled check on a real machine:** Tiled isn't installed here. The files follow the Tiled 1.10 format, and the `.world` uses Tiled's own JSON layout. Worth one open/edit/save round on the user's machine (does Tiled rewrite `.world` or the chunks; how does click-to-switch between chunks feel).
- **Reference image in the chunks:** it is only in the overview now. If it should also appear behind the chunks while painting, a script could cut per-chunk crops (150×150 px, shown scaled ×16 as a tile object in a `Reference` layer of each chunk). The reader would ignore that layer. Cheap, but it adds about 36 image files.
- Moving a POI across a chunk border needs cut and paste (Tiled can't drag objects between maps). `check.sh` catches objects dragged outside their chunk.
- Should the reference image stay in the game resources (`forge-gui/res`, 400 KB, shipped with the plane), or move to `docs/`/`tools/` with a relative path from the overview?
